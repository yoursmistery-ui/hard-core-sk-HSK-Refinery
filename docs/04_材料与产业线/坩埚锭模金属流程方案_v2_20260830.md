## 1 新流程（只到金属锭）

```
熔炼  金属原料(矿石/粗铁/废件) + 助熔/焦炭 + 空坩埚  →  熔融坩埚[该金属] + 炉渣
浇锭  熔融坩埚 + 锭模                              →  该金属锭 + 空坩埚(返还)
下游  现有全部配方不变——工具/装备/组件继续吃锭
```

坩埚与锭模都**可复用**（配方里"消耗 1 + 返还 1"，净零、无随机）。它们的作用是**产能节拍与前置投入**：手里有几个坩埚，就能同时开几炉；坩埚丢了/没做出来就停摆。这样"容器"的手感有了，又不用引入数值池。

## 2 关键技术结论（修正 v1）

**熔融金属必须"每金属一个 def"，不能用 stuff 复用同一个 def。** 两个硬理由：

1. `RecipeDef.products` 的产物 def 是**固定列表**，stuff 只能改变"产物本身由什么材料构成"，不能让同一个"锭"产物按投入变成 `青铜锭` / `坩埚钢锭` 这类**不同 def**；
2. `ThingFilter` 没有"按 stuff 过滤"的能力，浇注配方无法写成"只吃青铜的熔融坩埚"。

→ 规模因此是：**物品数 = 金属种数**，**配方数 = 金属种数 × 2**（熔炼 + 浇锭），外加坩埚/锭模 2 个载体与 2~3 条制模配方。首批建议 7 种：生铁、熟铁、泡钢、坩埚钢、锻钢、青铜、黄铜（乌兹钢与超级合金留后续）。合计约 7 物品 + 14 配方 + 3 载体配方，量级完全可控。

## 3 v1 的"配方数 = 形状 × 2"作废

那是"每种形状都能用任意金属浇"前提下的算法。现在形状只剩"锭"一种，直接按金属数展开更清楚，也不需要 stuff 沿链传递。v1 里关于"工具头带 stuff、成品工具染色"的整段推演一并作废。

## 4 "两槽容器"的两条路

| | 纯 XML（推荐） | DLL 真池（暂不做） |
|---|---|---|
| 金属液 | 熔融坩埚（每金属一 def 的实物） | `CompMoltenPool` float 池 + `FillableBar` |
| 废料 | 炉渣实物（已实装）+ 渣池 | 池内渣值，满则拨闸 |
| 槽位 | 建筑旁库存 / 坩埚架（直建存储） | 池容量 |
| 代价 | 只写 XML | 改 `Source/PetroInfraHSK.cs`（`NeedsWater`/`GasPort` 同类低频组件可仿）、重编译、性能铁律限低频；且**池记不了金属种类** |

## 5 工位与研究档

- 坩埚制作：陶工台 `PotteryStation` / `Ceramics_A1`（软粘土 + 碎石或耐火料）
- 锭模制作：陶工台 `Ceramics_A1`；原始档可另做石模 @石匠台 `Stonecutting`
- 熔炼：高炉 `TableFurnace`（铁系，`Metallurgy_B3`）／铸造厂 `Foundry`（有色金属，`Metallurgy_B4`）
- 浇锭：`Foundry`
- 每条新配方必须显式 `researchPrerequisite`，同一配方不挂两台（防 `duplicate unlocked defs` 与越级告警）
- ⚠ **不要往 `Kiln` 挂普通 RecipeDef**：Core_SK 把它声明为 `UniversalFermenterSK.ThingDef_UF`，会逐条刷 `should have Class=` 告警（上一轮实测踩过）
