§0 机制地基 已反编译验证

"决定 pawn 穿哪件"最终由这条加权链控制：

候选衣物(按 bodyPartGroup + tag 匹配过滤)
   → TryRandomElementByWeight(pa => pa.Commonality)
        → ThingStuffPair.Commonality
            = thingDef.commonality × thingDef.generateCommonality × stuff.commonality

Verse/ThingStuffPair.cs:44 证实 num *= thing.generateCommonality;。给每件衣服设 generateCommonality 即可精确控制同池出现比例——无需风格类目、无需补 Styleable comp、无需新贴图。

三条可叠加的挂载路径

路径载体粒度适用
A 职位服装现用PreceptDef[IdeoRole_*].roleApparelRequirements + allowedFactionCategoryTags + requiredTags/Defs派系tag + 职位军阀/骑士/美狐 NPC
B pawnKind 池PawnKindDef.apparel(RequiredTag/AlternateTagChoices{tag,chance})兵种/职业玩家开局兵、各职业鼠
C 权重底座核心每件 ThingDef.generateCommonality全局所有路径共用偏好底座
关键区别： requiredDefs/requiredTags 只圈定候选池；真正的偏好比例靠每件 def 的 generateCommonality 决定。这正是"xx 族偏好 xx 衣"的实现点。

§6 风险与边界 动手前必读

  • categoryTag 复用风险：RatkinStory 等被外交/生成引用；categoryTag 单值不可追加。→ 复用现有 tag + anyMemeRequired/pawnKind 区分，确需换 tag 时逐派系评估。
  • generateCommonality 是全局的：改高一件 = 对所有引用它的池都变常见。"A族常见 B族稀有同款" 必须靠不同 Culture tag 隔离池，不能只靠权重。
  • 无 tag 的 32 件：确认是否故意排除。
  • CE 数值：本方案纯改分配不碰 §7 CE，但美狐职位引用注意 CE。
  • 双目录同步：每步立即工作区↔部署 Mods 逐文件同步 + hash 核对。

§7 决策记录 已定案 2026-08-27

  1. tag 隔离池 + 池内权重（弃全局简化版）：派系差异由 pawnKind 池标签白名单/职位 requiredDefs 圈定，generateCommonality 只做池内梯度；典礼件 0.3 压低领袖池王冠频率属预期多样化。
  2. 不替换 03 的 requiredDefs：v5 三池 AND 结构实测稳定，权重直接作用于既有池内选择，零回归风险；Zone tag 留作后续槽位化/UI 分类维度。
  3. 美狐不重造、icon 沿用、弃 StyleCategoryDef 路线：Miho kind 原生 requiredTag+layer+alternateTagChoices 槽位制已满足"分区+偏好"；不产新图不建新文化。
