## 一、机制终态

| 环节    | v4                                                      | v5                                                                                  |
| ----- | ------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 阅读驱动  | 自写 `JobDriver_StudyBlueprint`（workType=Research，科研工作指派） | **原版 `JobDefOf.Reading` / `JobDriver_Reading`**（娱乐活动；自带动画、进度条、找椅子坐下、Read/Unread 双态） |
| 发起方式  | WorkGiver 自动排队 + 右键「研读」                                 | 自由活动由 `JoyGiver_Read` 派书 + 右键「指派阅读」（`job.playerForced`，固定 5000 ticks）               |
| 进度模型  | 「已读/未读」二值，集齐系列 → `unlock`                               | **连续 `bookProgress[book] ∈ [0,1]`**，逐 tick 累加，读一半存档保留                               |
| 解锁判定  | 集齐 → `CanStartNow = true`（还要上研究台）                       | 系列进度 100% → 解锁 + **直接完成该研究**（`FinishProject`，不耗科研点、不上研究台）                           |
| 数值层   | 无                                                       | 智力门槛 / 娱乐削弱 / 智力加成（三条，见 §二）                                                         |
| 科研树角标 | `已读 x/N`                                                | 解锁进度百分比，100% 变绿                                                                     |

进度公式（`BlueprintBookDoer.OnReadingTick`）：

```
factor = pawn.ReadingSpeed × 房间阅读加成 × delta      // 原版 Book.OnBookReadTick 传入
bookProgress[book]  +=  factor / readCost              // readCost 默认 5000
techProgress[tech]   =  Σ bookProgress[系列各书] / 系列本数
techProgress ≥ 1.0  →  解锁 →（finishOnUnlock）FinishProject
```

> 一次完整强制阅读（5000 ticks × 阅读速度 1.0）≈ +1.0 → 一本书读一遍即读完；  
> 阅读速度低的 pawn（视力/操作受损）需要分多次读完，房间阅读加成则加速。

## 三之二、硬门槛（v5.1，2026-09-10 修「队列绕过」）

### 症状

1. 上游门控科技锁着，但点它的**下游**节点后，上游被连带排进科研队列，然后照常研究。
2. 部分门控科技"没解锁也能研究"，部分又正常 —— 取决于你是直接点它还是经由下游连带入队。

### 根因（反编译 ResearchTreeSK + Assembly-CSharp 实证）

| # | 事实                                                                                                                                                                                    | 后果                             |
| - | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| ① | `ResearchTreeSK.Tree` 点击入队时调 `ResearchProjectDef.GetIncompleteParentsRecursive()`，**不检查可用性**                                                                                          | 点下游 → 锁着的上游一起入队                |
| ② | 队列推进直接 `ResearchManager.SetCurrentProject()`，该方法只判 `baseCost > 0`                                                                                                                     | 队列里的锁科技成为当前项目                  |
| ③ | `Node.Available` 只算 `TabInfoVisible && !Completed && HiddenPrerequisitesCompleted && 研究台/techprint/机械师/分析` —— **不含 `PrerequisitesCompleted`**，且是 ResearchTreeSK 自己算的，不看 `CanStartNow` | 置灰只能挡"直接点该节点"，挡不住连带入队          |
| ④ | `ResearchManager.ResearchPerformed` **不调用** `AddProgress`，而是自己 `progress[currentProj] = num`                                                                                          | 只拦 `AddProgress` 完全无效          |
| ⑤ | `ResearchPerformed` 在 `currentProj.IsFinished` 时**无条件** `FinishProject`，而 `FinishProject` 会**递归完成全部前置科技**                                                                             | 只要下游能攒满进度，上游锁着的门控科技被顺带完成 —— 跳关 |

### 修法（v5.1 新增，全部下沉到「进度层」）

```
BlueprintGateDatabase.BlocksResearch(ResearchProjectDef)  ← 统一判定
  ├─ ① !project.PrerequisitesCompleted          → 挡（防 ⑤ 的递归跳关）
  └─ ② IsGated(defName) && !IsTechUnlocked      → 挡（蓝图未读满）
```

| 补丁                          | 目标                                                                    | 作用                                         |
| --------------------------- | --------------------------------------------------------------------- | ------------------------------------------ |
| `Patch_ResearchPerformed`   | `ResearchManager.ResearchPerformed(float, Pawn)` Prefix               | 研究台劳动主路径（④）                                |
| `Patch_ResearchAddProgress` | `ResearchManager.AddProgress(ResearchProjectDef, float, Pawn)` Prefix | 其它进度入口（读书给科研、脚本加进度）                        |
| `Patch_WorkGiverResearcher` | `WorkGiver_Researcher.HasJobOnThing(Pawn, Thing, bool)` Postfix       | 不派人去研究，避免站台前按 0% 白刷智力经验                    |
| `Patch_TechprofCore`        | `CompUseEffect_FinishRandomResearchProject.DoEffect(Pawn)` Prefix     | 「科技专家副人格核心」不能跳过门控                          |
| `Patch_CanStartNow`         | `ResearchProjectDef.CanStartNow` getter —— **Prefix 改 Postfix**       | 补回被丢掉的 研究台/techprint/机械师/分析/IsHidden 等原版条件 |

### 两个刻意不做的决定

- **不改 `ResearchProjectDef.CanBeResearchedAt`**：原版科研页签用它生成「为什么不能研究」的原因列表  
  （`MainTabWindow_Research.lockedReasons`），在源头返回 false 会误报成 *MissingRequiredResearchFacilities*（缺少研究设施）。  
  改在 `WorkGiver_Researcher.HasJobOnThing` 收口，效果一样且不污染提示。
- **不拦 `ResearchManager.FinishProject` 本身**：这些正规流程都走它 ——  
  阵营起始研究标签 `FactionDef.startingResearchTags`、意识形态 `MemeDef.startingResearchProjects`、  
  archonexus 搬家（`ResetAllProgress` 后用 `ClassicStart` 标签恢复玩家已有科技）。  
  拦了会吞掉这些正统来源，所以只针对道具入口收口（`Patch_TechprofCore`）。

### 补丁挂载安全性

`TryPatch` 新增「参数类型」重载：显式锁定重载，且若解析到的 `DeclaringType` 不是目标类型  
（说明命中的是基类虚方法）就退到 `AccessTools.DeclaredMethod` 强制取本类型声明的那个 ——  
否则 Postfix 挂到基类虚方法上，对子类 override 不生效。

## 三之三、门控锁沿前置链向下游传播（v5.2，2026-09-10 晚）

### 症状

微电子学（电子 I）被蓝图锁着（有锁图标），但它的下游 **研究技术 III** 却显示成「可研究」（无锁）。  
即：门控锁只作用在自己身上，**没有继承给下游节点**。

### 根因（反编译 `ResearchTreeSK/Node.cs` 实证）

科研树节点的可用态是它自己算的，和原版 `CanStartNow` 完全无关：

```csharp
// ResearchTreeSK/Node.cs:312  UpdateCaches()
Available = TabInfoVisible && !Completed && HiddenPrerequisitesCompleted
          && PlayerHasAnyAppropriateResearchBench && TechprintRequirementMet
          && MechanitorRequirementMet && AnalyzedThingsRequirementsMet && !IsHidden;
```

**这里只有 `HiddenPrerequisitesCompleted`，没有 `PrerequisitesCompleted`** —— 是该 mod 的刻意设计：  
它允许「点下游节点 → `GetIncompleteParentsRecursive()` 自动把未完成的前置排进队列」。  
所以原版那种「前置没做完就灰着」的视觉效果，在科研树里**根本不存在**。

- 锁图标（`Assets.Lock`）：`Node.Draw` 里 `if (!flag3)` 才画，`flag3 = Completed || godMode || Available`
- 点击入队：`Tree.cs:489` 只判 `NodeClickInfo.MouseOverNode.Available`

→ 结论：v5.0/v5.1 只对「自己就是门控科技」的节点压 `Available=false`，非门控的下游节点一律不碰。  
以截图为例：`MicroelectronicsBasics`（门控）锁着 → 它的下游 `Research_table_C1`（研究技术 III，**非门控，设计上故意不给蓝图**，因为给科研速度节点上蓝图会卡死整条科研）就完全没人管。

### 修法

`BlueprintGateDatabase.IsGateLockedOnPath(ResearchProjectDef)` —— 把门控锁补成**传递闭包**：

```
locked(node) = (IsGated(node) && !IsTechUnlocked(node))
            || 任一(递归)前置 locked          // prerequisites + hiddenPrerequisites 都算
```

- **遇到「已解锁但还没研究完」的门控科技即停止传播**：那是正常前置，科研树「点下游自动排队」能正常处理，不该把下游一并灰掉。
- **逐帧记忆化**（`_gateLockMemo` + `Time.frameCount`）：科研树刷新会遍历全部节点，不能每节点重走一遍前置链。占位 `false` 防数据成环递归爆栈。
- `Patch_NodeUpdateCaches.Postfix` 由「只判自身门控」改为调用该判定。

### 影响面（新档最坏情况，脚本 `_tmp/bp_lock_cascade.py`）

数据源 = 运行时终态 `Mods/Unified.xml`（557 个 `ResearchProjectDef`）+ 本 mod 门控 XML：

| 指标               | 数量            |
| ---------------- | ------------- |
| 被锁节点（门控 + 下游闭包）  | **312 / 557** |
| 其中「非门控但被上游锁住」的下游 | 258           |
| 未锁               | 245           |
| 门控目标在终态中缺失       | 0             |

截图三节点的实测对照：

| 科技                             | 门控 | 被锁      | 直接前置                     |
| ------------------------------ | -- | ------- | ------------------------ |
| `Electricity`（电力工程 I）          | ✔  | ✔       | `Research_table_B2`      |
| `MicroelectronicsBasics`（电子 I） | ✔  | ✔       | `Electricity`            |
| `Research_table_C1`（研究技术 III）  | ✘  | ✔（传播所得） | `MicroelectronicsBasics` |

> 注：v5.1 的进度层 `BlocksResearch()` 已经含 `!PrerequisitesCompleted`，所以这 312 项**本来也涨不了进度**；  
> v5.2 修的是「显示与事实不一致」——灰的才是真的不能研究。

### 顺带：解锁瞬间即时刷新科研树

`ResearchTreeSK` 只在窗口 `PreOpen()` 里对全部节点调一次 `UpdateCaches()`。玩家读书时科研树往往正开着，  
不主动刷新就会出现「书已经读满，节点却还灰着/带锁」的错觉（要关窗口重开才更新）。  
新增 `BlueprintTreeRefresh.IfOpen()`：在 `CheckUnlock()` 解锁后 / `FinishProject` 完成后补一次全节点重算。  
纯反射实现（`ResearchTreeSK.Tree` 静态类 → `Initialized` 字段 + `Nodes` 属性 + `Node.UpdateCaches`），  
未装该 mod / 树未初始化 / 窗口未开一律直接返回，全包 try/catch。

## 三之四、原版「科研蓝图」归入「科技蓝图书籍」（v5.3，2026-09-10）

**需求**：把原版「科研蓝图」并入本 mod 的「科技蓝图书籍」分类树下 —— **仅改变分类归属、不改变任何物品效果**；  
本 mod 自有的 143 本蓝图体系保持不动、不与之混合。

### 现状（实测）

- 「科研蓝图」= 原版 Core 的 `ThingCategoryDef` **`Techprints`**（`<parent>Items</parent>`，中文 label「科研蓝图」）。  
  Core_SK 里同名定义**已被注释掉**，全 `Mods` 目录无人改过它的 parent。
- 其下物品 = **C# 动态生成**的 implied def —— `ThingDefGenerator_Techprints.ImpliedTechprintDefs()`，  
  `defName = "Techprint_" + 科技defName`，`thingCategories` **硬编码**为 `ThingCategoryDefOf.Techprints`。
- 终态共 **11 项** `techprintCount > 0` 的科技（Royalty 植入体/仿生系，前置均为 `Bionics`）：  
  `SpecializedLimbs`(专业肢体) `ArtificialMetabolism`(人工代谢) `CircadianInfluence`(作息节律)  
  `MolecularAnalysis`(分子分析) `BrainWiring`(大脑链接) `HealingFactors`(愈合因子) `VenomSynthesis`(毒素合成)  
  `SkinHardening`(皮肤硬化) `NeuralComputation`(神经计算) `CompactWeaponry`(紧凑武器) `FleshShaping`(躯体整形)
- 本 mod 分类树：`Books`(书籍) → `RK_BlueprintBooks`(科技蓝图书籍) → 5 个档位子分类。

### 为什么改「分类的 parent」而不是「物品的 thingCategories」

科研蓝图物品是 **implied def（C# 生成）**，不存在于任何 XML 文件里，而 `PatchOperation` 只操作 XML 文档 —— **够不着**。  
唯一纯 XML 通路 = 改 `Techprints` 这个 ThingCategoryDef 自己的 `parent`，让整棵子树搬进 `RK_BlueprintBooks`。

### 落地

`Patches/72_原版科研蓝图归入科技蓝图书籍.xml`（单条 `PatchOperationConditional` + `PatchOperationReplace`，  
xpath 存在性门控，`Techprints/parent` 不存在则整段跳过）：

最终分类树（脚本 `_tmp/verify_techprint_patch.py` 合并 Core + 本 mod 分类文件后模拟 patch 实测）：

```
Items
└─ Books (书籍)
   └─ RK_BlueprintBooks (科技蓝图书籍)
      ├─ Techprints              (科研蓝图)        ← 新并入
      ├─ RK_Schematic_Medieval   (中世纪研究图纸)
      ├─ RK_Blueprint_Industrial (工业蓝图)
      ├─ RK_Blueprint_Spacer     (太空蓝图)
      ├─ RK_Blueprint_Ultra      (极致蓝图)
      └─ RK_Blueprint_Archotech  (超凡蓝图)
```

### 为什么本 mod 体系「天然避开」这些蓝图

商人（`StockGenerator_BlueprintTrader.HandlesThingDef`）、任务奖励（`ThingSetMaker_BlueprintReward`）、  
科研门控、科研树角标 —— **全部基于 `BlueprintTargetExtension`（modExtension）筛选，与分类树无关**。  
科研蓝图没有这个 modExtension → 永远不会被选中。数据侧同样验证：11 项科技与本 mod 68 项门控科技**交集为 0**，  
其前置链上也没有任何门控科技（不会被 v5.2 传播锁牵连）。

### 未改变的东西

`techprintCount`、`CompTechprint`、研究台「应用科研蓝图」流程、商队 `StockGenerator_Techprints`、  
原版任务奖励池、存档里存储区筛选对 `Techprints` 分类的引用 —— 全部原样。

## 三之五、「科技典籍」——原版刷书途径接入 + 单本解锁（v5.4，2026-09-10）

### 需求

> 「把现有的刷出书的途径中，添加能够刷出解锁科技的书……就是普通书，类似美狐的书一样，读完就能把上锁解锁，可以研究，丰富解锁方式。」  
> 拍板三项：**独立单本解锁**、**目标科技刷出时随机绑定（只挑未解锁的）**、**概率要小（刷出书的概率中的小概率）**。

### 关键发现：原版只有**一个**随机刷书入口

反编译 `Verse/BookUtility`：

```csharp
public static Book MakeBook(ArtGenerationContext context, QualityGenerator? qualityGenerator = null)
{
    return MakeBook(GetBookDefs().RandomElementByWeight(x => x.GetCompProperties<CompProperties_Book>().pickWeight),
                    context, qualityGenerator);
}
private static List<ThingDef> GetBookDefs()
{
    return DefDatabase<ThingDef>.AllDefsListForReading.Where(x => x.HasComp<CompBook>()).ToList();
}
```

- 它按 `CompProperties_Book.pickWeight` **加权随机**，**不看 thingSetMakerTags、不看分类树** → 只要 def 留着非零 `pickWeight`，就会自己混进原版刷书池。
- 唯一的调用方是 `ThingSetMaker_Books.Generate`（原版任务奖励书籍堆，`ThingSetMakers_Reward.xml`）；商队书籍 / 书商库存走 `StockGenerator_Category(categoryDef=Books)`，也是同一批 def。
- 原版书籍只有 3 个 def：`TextBook`（教科书）/ `Schematic`（**科技图解书**）/ `Novel`（小说），可选参数 `pickWeight` 全部缺省 = 1。

**所以「加不进去」不是问题，「筛不了」才是。** 单纯给典籍一个 `pickWeight`，它会跟普通书同权被抽中，还会刷出**已经解锁**、读了没用的旧书。


### 修法

两段式：

**① 数据层**：54 本 `TechBook_<科技>`（`1.6/Defs/ThingDefs_TechBooks.xml`）

### 🔴 首次进游戏的致命修复（2026-09-10 16:5x）

**症状**：`Player.log` 54 条 `XML error: Could not find parent node named "Schematic" for node "ThingDef"`，  
另有 19 本 ×2 条 `Config error ... ends with a numerical digit`。

> `(?<![A-Za-z_])Name="..."` 收成一个集合，再逐个核本 mod 用到的每一个 `ParentName` 值。  
> 本次结果：`AdaptiveStorageBase` / `PrimitiveBase` / `MedievalBase` / `IndustrialBase` /  
> `SK.HitechMultiBaseDummy` / `RK_MeleeWeapon` 都另有定义，**只有 `Schematic` 全库无 `Name`**。

**修法**：

1. 自建抽象基类复刻原版外观（**不能直接继承 `Schematic`**）：  
   `<ThingDef ParentName="BookBase" Name="RK_TechBookBase" Abstract="True">` + 原版 `graphicData`  
   （`Things/Item/Book/Schematic/Schematic`，`Graphic_Single`，`drawSize 0.8`）+ `uiIconPath`；54 本改挂它。
2. 19 个以数字结尾的 defName（`Ballista_B1` / `Medicine_B2` / `Armor_D1` / `Stargate_F1` …）  
   统一加 `_Treatise` 后缀 —— 这些 def 从未成功加载过，任何存档里都不存在，改名零风险。
3. 脚本：`_tmp/fix_techbooks_parent.py`（一次性修复，带 `--check`）；  
   `_tmp/gen_techbooks.py` 同步改好（**重跑生成结果与修后文件逐字节一致**）；  
   `_tmp/verify_techbooks.py` 把原先那条自证式的 `assert ParentName == "Schematic"` 换成  
   「父节点必须在某个 XML 里以 `Name=` 真实存在」+ 「defName 不得以数字结尾」。

**顺带修正的校验脚本缺陷**（避免下次再被骗）：

- `verify_techbooks.py` 原先断言的是「生成器怎么写」，等于拿假设当标准答案 → 对 54 本全灭判「无异常」。
- `verify_v55_badge.py` 用 `root.iter("CompProperties_Book")` 找元素，而 `Class="CompProperties_Book"`

## 三之六、科研节点标识——蓝图/典籍像美狐书一样带小图标（v5.5，2026-09-10）

### 需求

> 「把所有科技节点的蓝图/图书 和美狐书一样加一个 科研节点标识，方便我后续查看和辨识。」

截图证据：交易列表里美狐的 `Miho_Schematic`（原版 Schematic 外观）名字右侧有一个**绿色小书图标**，  
而旁边的原版小说 / 教科书都没有。


### 定位：图标是 Dynamic Trade Interface 画的

装了 `Dynamic Trade Interface`（动态贸易界面）。它有一套 `MoreIconsDef` 机制：

```xml

<DynamicTradeInterface.Defs.MoreIconsDef>
  <defName>BookIconDef</defName>
  <getIconsCallbackHandler>...ColumnExtraIconTypes.BookDrawable:GetIcons</getIconsCallbackHandler>
  <searchValueCallbackHandler>...BookDrawable:GetSearchString</searchValueCallbackHandler>
</DynamicTradeInterface.Defs.MoreIconsDef>
```

反编译 `DynamicTradeInterface.dll` 的 `BookDrawable.GetIcons(Tradeable)`（ILSpy 实证）：

```csharp
Book book = tradeable.AnyThing as Book;
if (book == null) yield break;
int researchCount = 0, finishedResearchCount = 0;
foreach (var d in book.BookComp.Doers.OfType<ReadingOutcomeDoerGainResearch>())
    foreach (var proj in ValuesOf(d).Keys)        // 反射读 protected 字段 "values"
    { researchCount++; if (proj.IsFinished) finishedResearchCount++; }
if (researchCount > 0) {
    icon  = Textures.Schematic;                   // 绿色小书
    color = (finished == total) ? green : ((finished > 0) ? yellow : red);
    tip   = finished + "/" + total + " projects researched.";
}
```

**结论：判定条件只有一个** —— 书是 `Book`，且 `BookComp.Doers` 里含**原版** `ReadingOutcomeDoerGainResearch`，  
且它的 `values` 非空。颜色随 `project.IsFinished` **实时**变化（不改存档、不重启）。

### 为什么不能只改 XML

原版 doer 的项目表是**书生成那一刻**由 `ReadingOutcomeDoerGainResearch.OnBookGenerated` 算一次的  
（`Book.PostPostMake` / `PostQualitySet` → `GenerateBook` → `AppendDoerRules`），  
来源是 XML 的 `include` / `tabs` **静态清单**。

而我们有 **143 个蓝图 def 共用基类 comps**（`ThingDefs_BlueprintGates.xml` 里 `<doers>` 只出现 2 处，  
分别在 `RK_BlueprintBookBase` 与 `RK_BP_TierHighTech`），静态 `include` 写不出「逐本不同的科技」。

### 修法：XML 挂空 doer + C# 按 `targetTech` 逐本填

| 层   | 改动                                                                                                                                                                                       |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| XML | 蓝图 2 处基类 + 典籍 54 处 `<doers>` 各加一行 `<li Class="BookOutcomeProperties_GainResearch" />`（**空 include**）                                                                                     |
| C#  | 新增 `Patch_GainResearchTargeting`：Postfix 原版 `ReadingOutcomeDoerGainResearch.OnBookGenerated(Pawn)`，读 `book.def` 的 `BlueprintTargetExtension.targetTech`，把 `values` 清空后只填那一项（幂等：已含该科技则跳过） |
| C#  | 新增 `Patch_BookExposeData`：Postfix `Verse.Book.ExposeData`，**读档补齐** —— 升级前就已经造出来的书 `OnBookGenerated` 早就跑完了，`values` 永远长不出来，靠这里补                                                           |

`values` 的数值沿用原版 `BookUtility.GetResearchExpForQuality(品质)`（Normal=0.016/tick），  
这样书本信息卡的收益行是正常文案。

### 副作用与安全性（关键）

- **读书会顺带调 `ResearchManager.AddProgress(proj, amount, source = null)`** ——  
  正是 v5.1 门控锁定的那个重载。**上锁科技的书读起来收益为 0**（直接在 Prefix 被拦），  
  科技已解锁后才会正常加速，与原版 Schematic 手感一致。
- **不装 DTI 也有收益**：书本信息卡（`ITab_Book`）会列出「研究 XX: N/小时」，  
  等于多了一处「这本书对应哪项科技」的提示。
- **老存档兼容**：`Book.ExposeData` 补齐，读档后立刻生效，不需要重新造书。

### 颜色语义

| 颜色 | 含义                         |
| -- | -------------------------- |
| 红  | 该书对应的科技**尚未**研究完成（通常全是未完成） |
| 黄  | 部分完成                       |
| 绿  | 全部完成                       |

注意这与 v5.4 的「已解锁绿勾角标」是**两套独立视觉**，位置也不同：  
绿勾画在**物品图标右下角**（`Widgets.ThingIcon`），本图标画在**名字右侧**（DTI 自己的列）。

### 顺带发现

- `ReadingOutcomeDoerGainResearch.IsValid(project)` 的硬前提：`generalRules != null`、  
  `baseCost != 0`、`tabs` 为空则跳过页签判定、`project.TechprintCount == 0`。  
  **终态 557 项科技中，本 mod 涉及的 68 项全部满足**（见 §六之二 v5.5 静态验证）。
- `ResearchManager.AddProgress` 只有两个重载：`(ResearchProjectDef, float, Pawn = null)` 与  
  `(float, bool = false)`。读书走的是前者，与 v5.1 的补丁目标**完全一致**（无需再补）。
- `Dynamic Trade Interface` 还有 `PawnIconDef` / `GenepackIconDef` / `TechprintIconDef`  
  等同类图标位，机制相同（`MoreIconsDef` + 静态回调方法）。

protected Dictionary<ResearchProjectDef, float> values = …;   // 实例数据, Scribe 存盘

### 数据模型（v6）

- **书实例绑定 = 「同一个科技」的 1~2 个卷**（用户 00:10 追加约束：**不得跨科技**）。

  1. 先选科技 —— **加权随机，概率大头落在「尚未解锁（未读满）」的科技上**；
  2. 再在该科技的卷列表里随机取 **1~2 个不重复的卷**。

- ⚠ **存档格式变更**：用户明确「**不用兼容老存档，开新档**」。

> ✅ **精度：不需要**。用户明确「不用精确，只要随机的概率大头在未解锁上就行」→

### v6.1 红字修复：读书必崩的 NullReferenceException（2026-09-11 00:4x）

**症状**：读档进图后，小人一开始读书就刷红字（`JobErrorRecover.log` 里有完整堆栈）：

```
Exception in JobDriver tick for pawn 加涅 driver=JobDriver_Reading (toilIndex=4)
System.NullReferenceException
  at RimWorld.ReadingOutcomeDoerGainResearch.OnReadingTick (Verse.Pawn reader, System.Single factor) [0x00000]
  at Verse.Book.OnBookReadTick (...)
  at RimWorld.JobDriver_Reading.<ReadBook>b__17_1 (...)
currentJob=Reading A = Thing_Blueprint_Ultra_Cataphract_I3679600
```

**根因（存档取证 + 反编译双重确认）**

1. `ReadingOutcomeDoerGainResearch.values` 是 Scribe 托管的字典
   （`Scribe_Collections.Look(ref values, "values")`）。
2. 反编译 `Verse/Scribe_Collections.cs` 实证：字典字段在以下**两种**情况下会被
   **直接置成 `null`**：
   - `Scribe.EnterNode(label)` 失败（**存档里根本没有该节点**）→ `dict = null`；
   - 节点存在但带 `IsNull="True"` 属性 → `dict = null`。
3. 存档 `Autosave-5.rws` 里那本书正是：
   ```xml
   <thing Class="BlueprintUnlockHSK.BlueprintBook">
     <def>Blueprint_Ultra_Cataphract_I</def>
     <id>Blueprint_Ultra_Cataphract_I3679600</id>   <!-- 与崩溃日志一致 -->
     <values IsNull="True" />                        <!-- 字典是 null -->
   ```
   全档共 **2 处** `IsNull="True"`（另一本是 `SchematicBook_MedicineIV`）。
4. 原版 `OnReadingTick` 头一行就是 `foreach (var (proj, v) in values)` → 对 null 直接 NRE。
5. **恶性棘轮**：我们 v5.5 的 `Patch_GainResearchTargeting.Ensure()` 里写着
   `if (vals == null) return;` —— 看到 null 就放弃，于是字典**永远修不回来**，
   而且下次存档又写成 `IsNull="True"`，从此每次读档读书必崩。

**修法（两层）**

| 层 | 位置 | 作用 |
| - | - | - |
| ① 根治 | `Patch_GainResearchTargeting.Ensure` | `vals == null` 时**新建 `Dictionary` 并写回字段**（不再 return），再走原有的填充逻辑 |
| ② 兜底 | 新补丁 `Patch_GainResearchReadingTick` | Prefix 打 `ReadingOutcomeDoerGainResearch.OnReadingTick`：`values != null` 直接放行；为 null 时先尝试 Ensure，仍修不好就**跳过原版**，保证异常绝不外逸（覆盖非本 mod 的坏书） |

- 兜底的字段读取用 **Harmony 字段注入**（形参名 `___values`），编译期直取字段，
  正常路径**零反射开销**；反射只在「发现 null」的罕见分支才用。
- 修复点在 `PostLoadInit`（`Patch_BookExposeData` 已挂）与 `OnBookGenerated`（新建书）两处，
  均在 `Scribe.mode` 安全窗口内，不会与 Scribe 抢写。

**顺带修掉的告警**：`ResearchTreeSK :: redundant prerequisites for 混凝土 II: 电力工程 I`
- `混凝土 II` = **`Concrete_C2`**（不是 C1），其前置 = `[Concrete_C1, Electricity]`。
- 09-10 给 `Concrete_C1` 补了 `Electricity` 前置后，`Electricity` 成了 `Concrete_C1` 的祖先 →
  `ResearchTreeSK.CheckPrerequisites()`（`Tree.cs:1219`）判定 C2 的直接前置 `Electricity` **冗余**，
  刷黄字并在运行时把它从列表里删掉。
- 修法：在 `HSK修复整合/Patches/01_科技与名字.xml` 里把 `Concrete_C2` 前置改成只有 `Concrete_C1`
  —— 语义完全等价（电力仍由 C1 传递满足），告警消失。

**⚠ 通用铁律（已写回技能）**

> 凡是 **Scribe 托管的自有字段**（尤其是 `Dictionary` / `List`），读档后**可能是 `null`**：
> 存档缺该节点、或写成 `IsNull="True"`，`Scribe_Collections.Look` 都会把它置 null。
> 因此① 任何「补写/修正」逻辑**必须先处理 null（新建集合）而不是直接 return**；
> ② 不要假设字段初始化器 `= new Dictionary<>()` 能兜住 —— Scribe 会把引用整个换掉。


## 四、关键工程结论（原版反编译实证，`_tmp/acsharp_src`）

1. **1.6 的 `BookOutcomeDoer` 没有 `ApplyOutcome`** —— 唯一入口是逐 tick `OnReadingTick(Pawn reader, float factor)`（由 `Book.OnBookReadTick` 派发）。因此 v5 的进度累加就在 `OnReadingTick` 里做，不需要自己造「读完事件」。
2. **`factor = pawn.GetStatValue(ReadingSpeed) × roomBonusFactor × delta`** —— 阅读速度与房间加成天然进入进度，无需额外写。
3. **智力门槛必须双点拦截**：`BookUtility.CanReadBook` 只有两处调用（右键指派可用性 + `JobDriver_Reading` 每刻 EndCondition）；**joy 自动派书走的是 `JoyGiver_Read.TryGiveJob → BookUtility.TryGetRandomBookToRead → 私有 `IsValidBook\`\`**。只拦 `CanReadBook` 会导致「自动塞书 → 开读 1 刻被中断 → 立刻重试」的抽搐循环。故补 `IsValidBook` prefix。
4. **`ReadingPolicy.effectFilter` 不会挡我们的书**：它由 `new ThingFilter(BookEffects, onlySpecialFilters: true)` 构造，而 `ThingFilter.Allows(Thing)` 在 `onlySpecialFilters` 时**跳过 def 白名单判定**（`if (!Allows(t.def) && !onlySpecialFilters) return false;`），故自定义 doer 的书仍可被 joy 选中。
5. **`BlueprintBook` 覆盖了 `GenerateBook`**（固定书名，不做 grammar）→ 原版 `ReadingOutcomeDoerJoyFactorModifier` / `BookOutcomeDoerGainSkillExp` 的 `OnBookGenerated` **不会执行**。所以娱乐削弱不能靠原版 doer，必须在 `PostPostMake` / `SpawnSetup` / `ExposeData.PostLoadInit` 三处显式 `SetJoyFactor`。
6. **Harmony 参数绑定用位置式**（`__0/__1/__2`）而非形参名，避免反编译产物丢名导致补丁静默失败；全部新补丁经 `TryPatch` 带 try/catch 挂载，单个失败只记警告。

### 顺带修掉的 v4 潜在 bug

- `Patch_CanStartNow` 未判 `IsFinished` → 已完成的研究会被判成「可研究」，科研树可能允许重复点击。v5 补 `IsFinished` 短路走原逻辑。
- `Patch_NodeUpdateCaches` / `Patch_CanStartNow` 对非门控科技也生效 → v5 增加 `gate` 判定。
- `BlueprintStuckMonitor` 把非门控科技也算「卡点」→ v5 跳过。
