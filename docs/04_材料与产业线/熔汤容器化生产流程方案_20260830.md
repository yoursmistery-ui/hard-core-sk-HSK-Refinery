# 熔汤容器化生产流程方案（2026-08-30）

> 状态：**已被 v2 取代**（2026-08-30 用户简化：模具只保留锭模、去掉工具模具）→ 现行方案见 `坩埚锭模金属流程方案_v2_20260830.md`（未实装）｜上承《TFC模具铸造三段链》《TFC冶铁链统一改造清单》
> 用户新方案：① 所有冶炼厂做成**一个容器、两槽（金属液 / 废料）**；② 配方消耗金属液 → 出**工具头**；③ 工具头 + 木板 → 工具；④ **所有金属**都签进这套流程；⑤ 原始时代内容少，可逐档适配；⑥ 海量模具与配方需要一套"配方配合"体系。

## 1 一句话结论

**"槽里存金属液"这件事，用 float 池做不出"所有金属"，用"可带 stuff 的舀包/坩埚"能做，而且顺手把配方数从 形状×金属 压回 形状×2。**

原因：RimWorld 的 stuff（材料）系统挂在**实物 Thing** 上。一个数值池只能记"多少升"，记不了"这是什么金属"——要保留金属种类，池就得按金属分槽（青铜池、钢池、乌兹池……），槽数直接爆。反过来，只要"金属液"是一个**实物**（舀包/坩埚），它的 `.stuff` 字段天然携带金属身份，并沿链条自动传递：

```
熔炉   金属锭/矿石 ×N  →  舀包[stuff=青铜]        ← 一条配方吃任意金属
浇筑   舀包[stuff] + 模具 → 工具头[stuff] + 炉渣   ← 一条配方服务所有金属
装配   工具头[stuff] + 木板 → 成品工具[stuff]
```

配方数 = 形状数 × 2，**与金属种数无关**。这就是"一套配方配合海量模具"的解法。

## 2 两槽容器的两条实现路

| | A 纯 XML（推荐先做） | B DLL 真池（可选后置） |
|---|---|---|
| 金属液 | `RK_Met_Ladle` 舀包/坩埚（stuffable 实物，堆叠、可搬、显示为对应金属色） | `CompMoltenPool` 双 float 池 + 两条 `FillableBar` |
| 废料 | 已实装的炉渣实物 + 渣池（限定 filter 的存储建筑） | 池内渣值，满则拨闸停产 |
| 金属种类 | stuff 自动携带，**零额外 def** | 必须按金属分槽 → 槽数爆炸，或丢属性 |
| 进度条 | 检视面板库存 + 渣堆实物（RimWorld 原生观感） | 地图上两条条（`drawFuelGaugeInMap` 同款画法） |
| 成本 | 只写 XML，走既有补丁流程 | 改 `HSK工业科研大修/Source/PetroInfraHSK.cs`（已有 `NeedsWater`/`GasPort` 同类低频组件可仿），重编译 + 双目录同步 + 性能铁律（低频轮询/短路） |

> 若最终要"池"的手感，B 可以叠在 A 之上：舀包仍然承载 stuff，池只做**容量与积压显示**。别一上来做 B。

## 3 让 stuff 真的生效的前置（已核实）

`TFJ_Tool_Hoe` 等 STL 工具 def **当前没有 `<stuffCategories>`**，所以 Vile 的 `Cast_*` 虽然吃 `cat:CastBar`，铸出来的锄头仍然是"无材料"的同一把锄头。但它的贴图是 `CutoutComplex` + 有 `Hoe_m.png` 颜色遮罩——**补一行 `<stuffCategories>` 就白拿"青铜锄 vs 钢锄"的颜色与价值/近战差**。

注意边界：stuff 影响 `MarketValue`/`Mass`/近战 `power`/护甲值；**不影响 STL 的工作效率**（砍树速度在 modExtension 里，与 stuff 无关）。要让高级金属真的"更好用"，只有两条：给工具头按档分 def（def 膨胀），或接受"高级金属=更贵更硬的武器、效率相同"。建议后者，把差异落在武器/护甲侧。

## 4 模具的规模化（三档材质 × 形状）

TFC 本身就是分档的，正好拿来做科技阶梯，且**模具材质只影响"能不能浇高熔点金属"**：

| 档 | 材质 | 制作 | 复用 | 可浇金属 |
|---|---|---|---|---|
| 原始 | 打制石模 | 石匠台（`Stonecutting`） | 一次性、浇完即碎 | 铜、锡、青铜（低熔点） |
| 陶 | 烧制粘土模 | 陶工台（`Ceramics_A1`） | 一次性 | 铁、钢 |
| 铁 | 金属型（铁模） | 铸造厂（`Metallurgy_B4`） | 可反复用（配方里模具既消耗又产出） | 全部，含高熔点 |

"可反复用"在纯 XML 里的合法写法：浇筑配方消耗 1 个铁模、产物里再给回 1 个铁模——净消耗为零，直观且无随机。原始档只能浇低熔点金属，就用"高熔点金属的浇筑配方不认石模"实现（不同配方挂不同模具 filter），**静态可预期**。

## 5 配方配合体系（CSV 驱动生成器）

不手写几百条配方。唯一真源是一张表，脚本产 XML：

`_tmp/met_line_data/molds.csv`

| 列 | 例 | 说明 |
|---|---|---|
| `shape` | `Hoe` | 形状键，决定 defName / 贴图名 |
| `cn` | 锄头 | 中文名 |
| `mold_tier` | `stone,clay,iron` | 该形状有哪些档模具 |
| `mold_tex` | `锄头模具` | 对应 TFFH 素材文件名 |
| `head_ingredients` | `WoodPlank×1,FluxPowder×2` | 装配段额外料（柄/焊剂） |
| `product` | `TFJ_Tool_Hoe` | 最终成品 def（可空=新建） |
| `metal_work` | `35` | 每件吃多少金属（克当量） |
| `slag` | `3` | 每件产多少渣 |
| `research` | `RKHSK_Tools_Medieval2` | 各段研究档 |
| `bench` | `FueledSmithy` | 装配工位 |

`_tmp/met_line_gen.py` 按表产 `Items_RK_Met_Molds.xml` / `Recipes_RK_Met_Molds.xml`，并同步产 `_tmp/met_line_check.py` 的期望清单（defName 唯一性、引用完整性、研究档不越级）。**改数值改表，不改 XML**；新增一个形状=加一行。

## 6 分期落地（每期独立自验）

- **P0 前置**：封 `Steel` 捷径（《统一改造清单》Step4，`MakeSteelBars_Hand` 手锻台出钢锭）——不封，整套新流程被一条原始档配方绕过；同时给要走的工具/武器补 `<stuffCategories>`。
- **P1 熔汤实体化**：`RK_Met_Ladle`（stuffable）+ 熔炉配方「任意 `*Bar`/矿石×N → 舀包 + 炉渣」+ 坩埚架（直建存储，按"能直建就不进工作台"）。
- **P2 浇筑改造**：已实装的 5 套模具链，把"吃 `cat:CastBar`"改成"吃舀包"，产物由"铸件毛坯"改名"工具头"并带 stuff。
- **P3 装配**：工具头 + `WoodPlank` → 成品工具（stuff 传递，颜色自动变）。
- **P4 规模化**：CSV + 生成器接剩余 11 套模具；补原始档（石模 + 铜/青铜/黑曜）。
- **P5 可选**：DLL 双池容器（真进度条）。

## 7 风险与边界（先说清）

1. **改动面**：环境里 1759 条配方、88 项金属、本 mod 147 件装备。若要求"所有金属都走熔汤"，会把装备/组件/弹药一起卷进来。建议**只让"工具头/武器头/铸件"这一类走新流程**，其余照旧吃锭，否则重构范围失控。
2. **`CastIron` 教训**：改 `CastBar` 成员会牵动 41 条铸造配方；熔汤化之后 `CastBar` 的角色要重新定义（建议：`CastBar` 退化为"可直接浇的金属锭"集合，工具头另立 `RK_Met_Heads` 分类）。
3. **Kiln 雷**：Core_SK 把 `Kiln` 声明为 `UniversalFermenterSK.ThingDef_UF`，普通 RecipeDef 挂上去会刷告警——新配方别往窑上挂，用陶工台/铸造厂。
4. **ResearchTreeSK**：每条新配方必须显式 `researchPrerequisite`，且同一配方不要挂两台，防 `duplicate unlocked defs` / 越级告警。
5. **存档**：按项目铁律不为旧存档做兼容，改坏了直接开新档。
