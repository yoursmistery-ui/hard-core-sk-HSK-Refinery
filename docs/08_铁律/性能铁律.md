# 性能铁律(HSK 整合)

> 来源: AGENTS.md §8(2026-08-21 用户要求: 性能第一)。所有在高频 tick 中刷新或判定的逻辑,必须清理成低频限定条件逻辑,减少性能损耗;与功能正确性冲突时,先保证方案低耗可行。

## 1. 降频
- 普通逻辑一律**低频轮询**(tick 计数取模,如每 60/120/300 ticks),绝不每 tick 全量执行。
- 仅移动/战斗等确实必须的逻辑保持高频。

## 2. 事件驱动
- 能用事件/回调触发的刷新**绝不轮询**;`Tick()` 内只做轻量"是否需要重算"判定。

## 3. 提前短路
- 判定先过**最便宜的条件**(无相关 pawn/建筑/comp 激活 → 直接 return),昂贵遍历/计算放最后。

## 4. 缓存复用
- 高频读取的昂贵结果(路径/材质/属性/字典查找)缓存,仅在低频校验点或事件时失效重建。

## 5. 禁每 tick 遍历
- **不每 tick 遍历** map / 全部 pawn / 所有建筑;用索引、缓存列表,或把遍历降频到秒级。

## 6. 写 DLL 自查清单
- `Tick()` / `CompTick()` / `GameComponentTick()` 内出现以下任一 → **必须先按本准则重构再提交**:
  - 遍历(map/pawn/建筑全量)
  - 反射
  - LINQ 全量查询(`Where`/`Select` 每 tick)
  - 频繁字符串拼接
  - 每 tick 构造字典/集合

## 7. 参考实现
- Processor Framework 的 `CompTick` 仅 18 条指令,空机/关机直接短路,每 60/250 tick 才做实质工作,无每 tick 全量遍历(详见 `docs/03_生产框架/ProcessorFramework框架梳理.md` §7),符合本铁律。
